## 📌 1. 데이터 수집 원천 및 수집 데이터 분류

빅데이터 수집 아키텍처 설계의 첫걸음은 원천 데이터가 어디에 존재하고($Source$), 어떤 데이터 형식($Format$)을 띠고 있으며, 수집 주기($Cycle$)는 어떠한지 명밀하게 분류하는 것입니다.

### (1) 데이터 수집 원천 분류

* 내부 데이터 (Internal Data): 사내 핵심 비즈니스 프로세스를 수행하기 위해 구축된 인프라 내에 존재하는 데이터셋입니다.ERP (Enterprise Resource Planning, 전사적 자원 관리): 생산, 물류, 재무, 인사 등 전사적 경영 자원을 통합 관리하는 데이터 원천입니다.
* CRM (Customer Relationship Management, 고객 관계 관리): 고객 정보, 구매 이력, 마케팅 캠페인 반응률 등 고객 행동과 밀접한 정형 데이터 원천입니다.
* SCM (Supply Chain Management, 공급망 관리): 자재 조달, 부품 적재, 물류 유통망의 흐름과 연계된 실시간 정형·반정형 데이터 원천입니다.
* DW (Data Warehouse, 데이터 웨어하우스): 현업 시스템(OLTP)에서 추출 가공된 데이터들을 전사적 의사결정 분석(OLAP)을 위해 주제별로 통합 저장해 놓은 대용량 정형 저장소입니다.
* 외부 데이터 (External Data): 사내 통제망 밖에 존재하지만 기상 정보, 유가, 환율, SNS 트렌드 분석 등 비즈니스 예측력을 극대화하기 위해 실시간 수집 연동해야 하는 외부 데이터셋입니다.종류: 기상청 기후 API, 공공데이터 포털 데이터, SNS 크롤링 데이터, 경쟁사 가격 모니터링 데이터 등

### (2) 데이터 형식별 기술적 분류

데이터 유형데이터 형식메타데이터(스키마) 포함 여부주요 특징 및 비즈니스 예시**정형 데이터 (Structured)**RDB, CSV, Spread Sheet**포함됨 (엄격한 스키마)**관계형 데이터베이스 테이블 구조로 저장되며, 행(Row)과 열($Column$)로 완벽히 규격화된 수치 중심 데이터입니다.**반정형 데이터 (Semi-Structured)**JSON, XML, HTML, 로그 파일**포함됨 (유연한 자가진술 스키마)**고정된 하드웨어 릴레이션 테이블은 없으나, 데이터 내부에 키-값(Key-Value) 쌍이나 태그(Tag)의 형태로 스키마가 존재하여 컴퓨터가 파싱(Parsing)하기 쉬운 구조입니다.**비정형 데이터 (Unstructured)**이미지, 동영상, 음성, 텍스트 문서**포함 안 됨**고정된 규칙이나 형태가 전혀 없고 수치나 태그로 표현하기 어려운 대용량 파일 중심 데이터로, 딥러닝 등의 전처리를 통해서만 피처 추출이 가능합니다.

## 📌 2. 데이터 측정 척도와 통계적 제약성

원천 데이터의 각 피처($Feature$)가 어떤 측정 척도(Scale of Measurement)를 사용해 가공되었는지에 따라, 데이터 전처리 단계 및 향후 통계학적 검정 기법의 적용 가능 범위가 엄격하게 지배됩니다.

* ```text
[측정 척도 분류 체계]
├── 범주형 (Categorical)
│   ├── 명목 척도 (Nominal) ── 사칙연산 불가, 오직 빈도수(최빈값) 계산만 가능
│   └── 순서 척도 (Ordinal) ── 대소 비교 가능, 연산은 불가 (중위수 계산 가능)
└── 수치형 (Numerical)
    ├── 등간 척도 (Interval) ── 사칙연산 중 (+, -) 가능, 절대 영점이 없음 (평균 계산 가능)
    └── 비율 척도 (Ratio)    ── 사칙연산 (+, -, *, /) 모두 가능, 절대 영점 존재
```

### (1) 범주형 척도 (Categorical Scale)

명목 척도 (Nominal Scale): 속성의 분류 및 구분을 위해 임의로 명칭이나 기호를 부여한 척도입니다.제약성: 어떠한 수리적 크기가 없으므로 사칙연산 및 대소 비교가 완전히 불가능하며, 오직 데이터의 빈도수(최빈값) 및 일치 여부(= 또는 =)만 확인할 수 있습니다.
* 예시: 성별 (남=1, 여=2), 혈액형 (A,B,O,AB), 우편번호, 축구선수 등번호
* 순서 척도 (Ordinal Scale): 명목 척도의 구분을 넘어, 대소 관계 및 서열(순위) 정보를 추가로 지닌 척도입니다.제약성: 대소 비교(>$또는$
* 예시: 학점 (A+>A0>B+), 설문지 만족도 (매우 불만족 =1, 보통 =3, 매우 만족 =5), 소득 수준 (상, 중, 하)

### (2) 수치형 척도 (Numerical Scale)

* 등간 척도 (Interval Scale): 속성 간의 서열뿐만 아니라 수치 간의 간격이 산술적으로 일정한 등간격을 가진 척도입니다.제약성: 수치 간의 사칙연산 중 오직 덧셈과 뺄셈(+,−)만 연산이 의미를 가집니다. '절대 영점(Absolute Zero Point)'이 존재하지 않기 때문에 나눗셈이나 곱셈(∗,/)의 비례 관계가 성립하지 않습니다. (예: $10^\circ\text{C}는$5∘C보다 5만큼 더 따뜻한 것이지, 2배 더 뜨거운 것이 아님) 대표값으로 산술평균(Mean)을 구할 수 있습니다.
* 예시: 온도(∘C), 지능지수(IQ), 서기 연도
* 비율 척도 (Ratio Scale): 등간 척도가 지닌 등간격의 성질에 더해, **아무것도 존재하지 않는 상태를 의미하는 '절대 영점(Absolute Zero Point)'**이 수학적으로 확보된 최고 단계의 척도입니다.제약성: 절대 영점이 존재하므로 사칙연산(+,−,∗,/)이 모두 무결하게 성립하며, 비율 비교(예: $10\text{kg}은$5kg보다 2배 더 무겁다)가 정확하게 가동됩니다. 사칙연산이 전부 되므로 기하평균, 조화평균 등 모든 통계 지표 산출이 가능합니다.
* 예시: 매출액, 무게(kg), 나이, 인구수, 연봉

## 📌 3. 하둡 에코시스템 기반 빅데이터 수집 기술 아키텍처

사내 서버에서 뿜어져 나오는 비정형 로그와 외부 데이터베이스의 정형 데이터를 하둡 분산 시스템(HDFS)으로 끌어오기 위해 활용되는 에코시스템 3대 수집 기술의 세부 메커니즘을 규명합니다.

### (1) Apache Flume (플룸): 실시간 비정형 로그 수집기

Flume은 데이터 소스에서 발생하는 실시간 비정형 로그 스트림을 수집하여 분산 타깃(HDFS 등)에 안정적으로 밀어 넣어주는 분산 수집 아키텍처입니다.

```text
[Flume 에이전트 내부 트랜잭션 수집 메커니즘]
┌─────────────────────────────────────────────────────────┐
│ Flume Agent                                             │
│ ┌──────────────┐       ┌───────────────┐       ┌──────┐ │
│ │  Source (웹) ├──────>│ Channel (메모리)├──────>│ Sink ├─┼───> HDFS (적재)
│ └──────────────┘       └───────────────┘       └──────┘ │
└─────────────────────────────────────────────────────────┘
```

* Flume Agent(에이전트)의 3대 핵심 컴포넌트:Source (소스): 외부 데이터 소스(Web Server, Syslog 등)로부터 비정형 원천 데이터를 직접 수집하여 Flume 내의 채널로 데이터를 주입하는 엔트리 포인트입니다.
* Channel (채널): Source와 Sink 사이에 존재하는 안전한 트랜잭션 버퍼(Buffer) 저장소입니다.메모리 채널 (Memory Channel): 인메모리 연산으로 속도가 극도로 빠르나, 에이전트 장애 발생 시 버퍼 내 데이터가 소실(Volatility)될 위험이 있습니다.
* 파일 채널 (File Channel): 버퍼를 로컬 디스크 파티션에 기록하여 다소 느리지만, 갑작스러운 전원 차단에도 영속성(Durability)을 보장하여 유실 없는 수집을 담보합니다.
* Sink (싱크): 채널에 임시 저장된 데이터를 꺼내 최종 수집 대상 플랫폼인 HDFS, HBase, Elasticsearch 등으로 적재하고 채널의 임시 데이터를 파기하는 아웃풋 포트입니다.
* 트랜잭션(Transaction) 무결성 기법:Source에서 Channel로 데이터를 밀어 넣을 때, 그리고 Channel에서 Sink로 데이터를 안전하게 전달할 때 두 번의 개별적인 '커밋(Commit)' 트랜잭션을 적용합니다.
* 만약 전송 중 네트워크 연결이 끊기면 트랜잭션이 즉각 롤백(Rollback)되어 데이터가 유실되지 않도록 보장합니다.

### (2) Apache Sqoop (스쿱): RDB와 Hadoop 간 벌크 전송 도구

Sqoop은 관계형 데이터베이스(Oracle, MySQL, MS-SQL 등)의 정형 데이터를 하둡 분산 파일 시스템(HDFS)으로 고속으로 복사해 오거나 반대로 하둡의 결과물을 RDB로 고속 적재하기 위해 구축된 전송 솔루션입니다.

* Map-Only 기반의 분산 전송 원리:Sqoop은 데이터 전송 명령을 받으면 내부적으로 하둡의 맵리듀스(MapReduce) 작업을 즉석에서 자동 빌드하여 생성 및 실행합니다.
* 이때, 데이터 적재 속도를 비약적으로 끌어올리기 위해 오직 '맵(Map)' 태스크만 활용하는 'Map-Only' 방식으로 동작하며, 불필요한 집계 작업이 일어나는 '리듀스(Reduce)' 단계의 셔플링(Shuffling) 오버헤드를 아예 거치지 않습니다.
* 하둡 데이터 노드의 연산 자원과 병렬 네트워크 자원을 분산하여 활용하기 때문에 기존 단일 전송 서버 대비 극적인 병렬 고속 적재(Bulk Import/Export) 성능을 확보하게 됩니다.

### (3) Apache Kafka (카프카): 고성능 분산 스트리밍 메시징 플랫폼

Kafka는 다수의 데이터 프로듀서(발행자)와 다수의 데이터 컨슈머(소비자) 간의 높은 결합도를 완전히 제거하여, 수많은 서버들의 실시간 데이터 흐름을 대규모 비동기 방식으로 중계 제어하는 분산 메시징 플랫폼입니다.

* 발행-구독(Publish-Subscribe) 아키텍처:프로듀서(Producer)가 카프카 내부의 특정한 주소지인 **'토픽(Topic)'**에 메시지를 던져두면(발행), 컨슈머(Consumer)는 자신이 구독하고 있는 토픽에서 메시지를 원하는 시점에 비동기적으로 가져가서(소비) 적재합니다.
* 프로듀서와 컨슈머가 직접 연결되어 대기하지 않으므로 한쪽 시스템이 터지거나 부하가 발생해도 전체 메시징 파이프라인의 안전성이 고스란히 담보됩니다.
* 토픽(Topic)과 파티션(Partition) 및 오프셋(Offset):파티션 (Partition): 하나의 토픽을 물리적으로 여러 장치에 수평 분할하여 나누어 담는 구조입니다. 이 덕분에 여러 파티션에 대해 동시에 병렬 쓰기/읽기가 작동하여 디스크 병목 및 대역폭 제한을 원천 격파합니다.
* 오프셋 (Offset): 파티션 내로 유입되는 개별 메시지들에 대해 부여되는 유일하고 연속적인 정수 식별 번호입니다. 컨슈머는 이 오프셋 포인터를 기반으로 메시지를 어디까지 읽었는지 독립적으로 트래킹할 수 있어 중복 소비 및 누락을 지능적으로 자체 제어합니다.
* Apache ZooKeeper (주키퍼)의 통제:카프카 분산 브로커들의 상태 정보를 감시하고, 파티션 리더(Leader) 노드 장애 시 투표를 통해 백업 노드를 즉시 리더로 승격시키는 분산 코디네이션 및 상태 제어를 담당합니다. (최근 Kafka 아키텍처는 KRaft를 사용하여 ZooKeeper 독립 구조로 점진적 고도화 중입니다.)

### (4) 기타 대표 빅데이터 수집 및 이벤트 처리 기술 (★ 초빈출)

실무 및 시험에서 수집 파이프라인 설계나 예상 문제에 빈번하게 등장하는 고유 컴포넌트 기술들입니다.

* **`CEP (Complex Event Processing, 복잡한 이벤트 처리)`**:
  * 사내 여러 채널에서 끊임없이 뿜어져 나오는 대량의 원천 비정형 이벤트 데이터를 **물리 저장소에 영구 적재하기 전에, 인메모리 상에서 실시간으로 스트리밍 제어하여 미리 정의된 업무 규칙(Rule)이나 특정 패턴에 일치하는 유의미한 비즈니스 이벤트만을 자동으로 필터링 및 조기 식별**해 내는 실시간 이벤트 감지 기술입니다.
* **`Scrapy (스크래피)`**:
  * **파이썬(Python) 언어 기반의 강력한 오픈소스 비정형 웹 데이터 수집 프레임워크**입니다. 웹 사이트의 HTML 구조를 지능적으로 분석하여 소셜 데이터, 게시판, 뉴스 등의 웹 문서 콘텐츠를 초고속 수집하는 정밀한 크롤링(Crawling) 및 파이싱(Parsing) 수집 솔루션입니다.
* **`Logstash (로그스태시)`**:
  * 엘라스틱 서치(Elasticsearch) 등과 연계되는 ELK 스택의 핵심 실시간 파이프라인 수집 엔진입니다. 다양한 형태의 소스 서버로부터 유입되는 실시간 로그 데이터를 수집하고(Input), 가명처리나 변환 등 사후 가공을 수행한 후(Filter), 지정된 빅데이터 저장소에 벌크 적재(Output)하는 고속 데이터 전달 가교 역할을 수행합니다.
* **`Fluented (플루언티드)`**:
  * 트레저 데이터(Treasure Data)사에서 개발한 크로스 플랫폼 오픈소스 데이터 수집 소프트웨어로, JSON 포맷을 기본으로 모든 수집 데이터를 경량화하여 전달합니다.
* **`Scribe (스크라이브)`**:
  * 페이스북(Facebook)에서 최초 개발하였으며, 다수의 소스 서버로부터 생성되는 대규모의 실시간 스트리밍 로그 데이터를 고성능으로 분산 저장소에 동적 전송하는 대표적인 실시간 대용량 로그 수집기입니다.

## 📌 1. 하둡 분산 파일 시스템 (HDFS) 아키텍처

빅데이터 저장 기술의 사실상 표준인 HDFS(Hadoop Distributed File System)는 저사양 범용 서버들을 네트워크로 묶어 대규모 저장 공간을 구성하고, 대용량 파일을 분산 저장하여 고속 병렬 처리를 지원하는 자바 기반 분산 파일 시스템입니다.

### (1) HDFS의 분산 노드 구성 및 역할

HDFS는 철저하게 마스터-슬레이브(Master-Slave) 아키텍처를 기반으로 동작하며, 메타데이터 관리 노드와 실제 데이터 블록 저장 노드가 물리적으로 분리되어 작동합니다.

* 네임노드 (NameNode - Master): HDFS 전체 시스템의 브레인이자 컨트롤 타워입니다.역할: 파일 시스템의 디렉터리 트리, 파일 명, 파일별 저장 블록 목록, 그리고 블록들이 어느 데이터노드에 배치되어 있는지에 대한 위치 매핑 메타데이터를 메모리(RAM) 상에서 실시간 통제 관리합니다.
* 수행: 클라이언트의 파일 접근 요청을 중계하고 파일 열기, 닫기, 이름 변경 등의 네임스페이스 통제를 수행합니다.
* 데이터노드 (DataNode - Slave): 클라이언트가 업로드한 실제 대용량 데이터 파일들을 고정 크기 블록으로 쪼개어 분산 보존하는 일꾼 노드입니다.역할: 클라이언트의 물리적인 데이터 읽기/쓰기 요청을 로컬 디스크에서 수행하며, 주기적으로 네임노드에 자신이 살아있음을 증명하는 하트비트(Heartbeat) 신호와 현재 보존 중인 블록들의 메타 정보인 블록 리포트(Block Report)를 전송합니다.



### (2) HDFS 고가용성 (Active/Standby HA) 및 저널노드

기본 하둡 1.x 아키텍처에서는 단 한 대의 네임노드만 존재하여 네임노드 정지 시 전체 시스템이 마비되는 단일 장애점(SPOF, Single Point of Failure) 취약점을 지니고 있었습니다. 하둡 2.x부터는 이를 완전히 통제하기 위해 실시간 이중화(Active/Standby NameNode) 아키텍처를 적용했습니다.

* ```text
[HDFS Active-Standby NameNode 이중화 구조]
 ┌────────────────┐                     ┌─────────────────┐
 │ Active NameNode│                     │Standby NameNode │
 └───────┬────────┘                     └────────┬────────┘
         │      ┌─────────────────────────┐      │
         └─────>│ 저널노드군 (JournalNodes)│액티브 네임노드 (Active NameNode): 실제 클라이언트의 메타데이터 요청을 실시간으로 읽고 쓰며 시스템 전체를 지배하는 가동 상태의 노드입니다.
* 스탠바이 네임노드 (Standby NameNode): 액티브 노드가 무너질 경우를 대비해 실시간으로 메타데이터 상태를 완벽 동기화하고 대기 중인 콜드/웜 백업 노드입니다.
* 저널노드군 (JournalNodes): 액티브 네임노드가 갱신한 메타데이터 변경 이력(EditLog)을 중간에서 안전하게 공유 보존하는 공유 스토리지 저장소입니다. 스탠바이는 이 저널노드군을 지속해서 바라보며 실시간 동기화를 달성합니다.
* 주키퍼 & ZKFC (ZooKeeper Failover Controller): 각 네임노드에 설치된 ZKFC가 하트비트 연결망을 감시하다가 Active 네임노드가 폭사하면 즉시 ZooKeeper에 리더 선출 요청을 제기하여 Standby를 즉각 Active 상태로 안전하게 자동 격상(Failover)시킵니다.



  * NoSQL : 단어 뜻 그 자체를 따지자면 "Not only SQL"로, SQL만을 사용하지 않는 데이터베이스 관리 시스템(DBMS)을 지칭하는 단어이다. 관계형 데이터베이스를 사용하지 않는다는 의미가 아닌, 여러 유형의 데이터베이스를 사용하는 것이다.
  * 트랜잭션(transaction) : 데이터베이스의 상태를 변화시키기 위해 수행하는 작업의 단위

### (3) FsImage와 EditLog의 실시간 체크포인팅 과정

네임노드는 부팅 시 디스크에 영구 저장된 파일 시스템 이미지 파일($FsImage$)과 부팅 이후 변경된 모든 로그 원장 파일($EditLog$)을 메모리에 함께 올려 최종 메타데이터 맵을 가공해 냅니다. 하지만 하둡 시스템이 장기간 무중단 가동될 경우 EditLog의 크기가 무한히 비대해져 부팅 시 디스크 복구 시간이 기하급수적으로 밀리는 치명적인 연산 지연이 발생합니다.

이를 제어하기 위해 주기적으로 두 파일을 동기화 병합해 주는 프로세스를 **체크포인팅(Checkpointing)**이라고 하며, 전용 연산 기기인 보조 네임노드(Secondary NameNode) 혹은 Standby 네임노드가 이 과정을 도맡아 처리합니다.

```text
[Secondary NameNode 기반 체크포인팅 메커니즘]
① EditLog 롤링 (새 EditLog 파일 생성 및 기존 파일 쓰기 잠금)
② Active NameNode ── (FsImage, 기존 EditLog 다운로드) ──> Secondary NameNode
③ Secondary NameNode: 메인 디스크에서 두 파일을 머지(Merge)하여 새로운 FsImage 파일 생성
④ Secondary NameNode ── (머지 완료된 신규 FsImage 전송) ──> Active NameNode
⑤ Active NameNode: 기존 구형 FsImage를 파기하고 신규 수신한 파일로 즉시 대체(교체 완료)
```

## 📌 2. NoSQL 데이터베이스 4대 데이터 모델 비교 분석

기존 RDBMS는 엄격한 일관성(ACID)과 정규화된 릴레이션 테이블로 뛰어난 트랜잭션 품질을 보장하지만, 초고속 수평 확장(Scale-out)이 요구되는 대규모 비정형 웹 서비스 환경에서는 성능 병목을 마주하게 됩니다. NoSQL(Not Only SQL)은 스키마 리스(Schema-less) 설계와 확장성을 지향하여 수많은 고성능 데이터 스토어를 제공합니다.

### (1) Key-Value Store

데이터를 저장하는 지극히 원초적이고 극적인 단순 속도를 지닌 모델입니다.

* 구조 및 동작: 고유한 키(Key)와 이에 대응하는 불투명한 값($Value$)의 매핑 쌍으로 이루어진 구조입니다. 인덱스 검색 구조가 단순하여 O(1) 수준의 지연 없는 초고속 실시간 조회 성능을 제공합니다.
* 단점: 값($Value$) 내부의 필드 단위 조건 검색이나 내부 조인 연산이 완전히 불가합니다.
* 주요 엔진: Redis, Riak, DynamoDB
* 적합 시나리오: 실시간 세션 캐싱, 장바구니 정보 보존, 유저 실시간 접속 데이터 버퍼링

### (2) Document Store

키-값 구조에서 한 단계 더 나아가 값($Value$) 부분을 컴퓨터가 해석(Parsing)할 수 있는 구조적 텍스트 포맷으로 담아낸 구조입니다.

* 구조 및 동작: 데이터가 JSON, XML, BSON 등의 고도로 유연한 도큐먼트 형태로 관리됩니다. 도큐먼트 내부에 무수한 중첩 객체(Nested Object)와 배열 저장이 가능하며, 스키마 리스 상태이므로 문서마다 다른 구조의 키 필드를 지녀도 하드웨어 장애 없이 저장됩니다.
* 강점: 도큐먼트 내부의 특정 상세 필드를 탐색 인덱스로 지정하여 쿼리를 날릴 수 있는 강력한 인덱싱 기능을 제공합니다.
* 주요 엔진: MongoDB, CouchDB
* 적합 시나리오: 빈번한 스키마 확장이 일어나는 모바일 백엔드, 콘텐츠 관리 시스템(CMS), 실시간 로그 상세 조회 시스템

### (3) Column-Family Store (Wide-Column)

대규모 분산 클러스터 환경에서 가로 행이 아닌 세로 열($Column$) 단위로 데이터를 묶어 압축 저장하는 고효율 분산 디스크 전용 모델입니다.

* 구조 및 동작: 하나의 키 슬롯에 수많은 가변 열들(Column)이 들어갈 수 있는 유연한 구조를 취합니다. 동일 열 내의 데이터는 물리적 성향이 유사하므로 압축 효율이 기하급수적으로 우수하며, 수천 대의 하드웨어 클러스터 노드로 무제한 수평 확장이 작동합니다.
* 강점: 불필요한 행 전체를 읽는 디스크 입출력(I/O)을 무시하고, 통계 분석에 꼭 필요한 특정 컬럼만 선별 추출하여 고속 대용량 적재(Bulk Write/Read)를 돌릴 수 있습니다.
* 주요 엔진: HBase, Cassandra, ScyllaDB
* 적합 시나리오: 사물인터넷(IoT) 센서 실시간 스트리밍 대용량 로그 적재, 통계 분석 마트 구축

### (4) Graph Store

네트워크 토폴로지 상에 널리 퍼진 고밀도 객체 간의 관계와 고차원 상호 연결망을 추적하기 위해 특별히 고안된 수학적 위상 모델입니다.

* 구조 및 동작: 실체인 노드(Node, 정점)와 실체 간의 관계선인 에지(Edge, 간선), 그리고 각 개체가 지닌 고유 속성(Property) 구조로 정보를 저장합니다.
* 강점: 테이블 간의 조인($Join$) 연산이 무수히 얽힌 다대다(N:M) 복잡 관계망을 탐색할 때 연산 지연 없는 극강의 추적 성능을 발휘합니다.
* 주요 엔진: Neo4j, JanusGraph, Titan
* 적합 시나리오: 은행 실시간 사기 금융 거래(FDS) 이상 거래 자금 세탁 경로 추적, SNS 지인 인맥 추천 시스템

### (1) CAP 정리 (CAP Theorem)

에릭 브루어(Eric Brewer) 교수가 제안한 정리로, 대규모 분산 데이터베이스 환경은 다음 3가지 핵심 속성을 전부 만족시킬 수 없으며, **물리적으로 오직 최대 2가지만 선택하여 충족**할 수 있다는 네트워크 설계의 엄격한 한계 규정입니다.

```text
[ 일관성 (Consistency) ]
                             /\
                            /  \
                           / CA  -> 전통적 RDB (Oracle, MySQL)
                          /      \
                         /________\
 [가용성 (Availability)]        /  [분할 허용성 (Partition Tolerance)]
                            CP / -> HBase, Redis (네트워크 차단 시 일관성 선택)
                              /
                             \/
                        [ AP 모델 ] -> Cassandra, DynamoDB (장애 중에도 즉각 응답 보장)
```

* 일관성 (Consistency - C): 분산 클러스터 내의 어떤 노드에 읽기 쿼리를 던져도 전사 클러스터에서 항상 똑같이 업데이트된 최신화 상태의 데이터를 완벽하게 반환받는 성질입니다.
* 가용성 (Availability - A): 클러스터의 특정 서버 노드들에 대규모 네트워크 장애가 터져도, 정상 생존한 어떤 노드에 조회를 던지면 성공이든 실패든 에러 없이 즉시 합리적인 응답을 받을 수 있는 성질입니다.
* 분할 허용성 (Partition Tolerance - P): 각 노드 사이의 무선 물리 통신망에 대규모 단절(Partition) 장애가 발발해도 전체 분산 데이터 시스템은 단절 없이 온전하게 작동을 지속해야 하는 인프라적 전제 조건입니다.

> [!NOTE]
> 💡 현실적인 CAP 설계의 Trade-off: 분산 데이터베이스망에서 네트워크 단절 위험(P)은 거부할 수 없는 현실 물리적 상수로 고정됩니다. 따라서 모든 현대 분산 시스템 아키텍처는 사실상 "CP 모델" 또는 "AP 모델" 중 비즈니스 전략에 따른 치명적인 양자택일 노선을 밟게 됩니다.CP 선택: 네트워크 단절 시 데이터 불일치를 원천 방지하기 위해 장애 구간이 복구될 때까지 쓰기/읽기 연산을 통제하여 일관성을 사수합니다. (금융 거래 등)AP 선택: 네트워크 단절 시 일부 노드의 구형 데이터 조회 위험을 전제하더라도, 서비스가 끊기지 않도록 가용한 노드들을 통해 즉각 응답을 흘려보냅니다. (SNS, 실시간 댓글 등)

### (2) BASE 원칙: 완화된 대안 지향성

전통적 RDBMS가 엄격하게 사수해 온 원자성, 일관성, 고립성, 지속성인 **ACID 원칙**은 극적인 실시간 쓰기가 일어나는 수평 확장 분산 웹 환경에 그대로 적용하기가 거의 불가능합니다.

이에 대응해 CAP 정리의 연장선상에서 성능과 고가용성을 극대화하기 위해 탄생한 완화된 일관성 패러다임이 바로 **BASE 원칙**입니다.

* 기본적 가용성 (Basically Available - BA): 클러스터에 대형 통신 차단이 발생하더라도 완전 중단되는 대신, 일부 정상 가동 노드 영역을 통해 기본적인 서비스 조회 흐름은 언제나 유지하는 설계 사상입니다.
* 소프트 상태 (Soft State - S): 데이터가 외부 연산 이벤트에 의해서만 강제 갱신되는 것이 아니라, 백그라운드의 동기화 프로세스에 의해 스스로 점진적으로 흐르며 전파 변경될 수 있는 자율적 유연 상태입니다.
* 최종 일관성 (Eventual Consistency - E): 특정 시점 순간에는 일시적인 불일치가 발생할 수 있으나, 일정 유휴 기간이 지나면 종국에는 전사 분산 노드 전체가 동일한 일치값으로 조화롭게 수렴(Eventual Converge)하는 평화로운 일관성 도달 설계 기법입니다.

## 📌 1. 전사 데이터 거버넌스(Data Governance) 체계

수집 및 적재 아키텍처가 물리적인 인프라를 의미한다면, **데이터 거버넌스**는 사내에 존재하는 방대한 데이터가 엉키거나 썩지 않도록 통제하고 자산화하는 **'조직적·제도적 관리 체계'**를 의미합니다.

(Partially Synthetic Data) | 원본 데이터 중 일부 데이터(민감 데이터)만 재현 데이터로 대체한 데이터
(Hybrid Synthetic Data) | 일부 변수들의 값을 재현 데이터로 생성하고, 생성된 재현 데이터를 실제 데이터 모두 
이용하여 또 다른 일부 변수들의 값을 다시 도출하는 방식으로 생성한 데이터

### (1) 데이터 거버넌스 수립의 목적 및 필요성

* 데이터 사일로(Silo) 제거: 부서별로 데이터가 격리되어 전사적 활용이 가로막히는 현상을 예방합니다.
* GIGO(Garbage In, Garbage Out) 통제: 유실되거나 정합성이 깨진 쓰레기 데이터가 적재되어 분석 모형의 예측력을 오염시키는 현상을 통제합니다.


### (2) 데이터 거버넌스 4대 핵심 구성요소

데이터 거버넌스를 완벽히 가동하기 위해서는 아래의 4가지 유기적 축이 결합해야 합니다.

* ```text
┌────────────────────────────────────────────────────────┐
│               [데이터 거버넌스 4대 구성요소]               │
│                                                        │
│  1. 원칙 (Principle)  ◀─── 표준 가이드라인, 규칙 수립     │
│  2. 조직 (Organization) ◀─── R&R(역할과 책임), 의사결정 기구 │
│  3. 프로세스 (Process)  ◀─── 데이터 수명주기 표준 절차       │
│  4. 인프라 (Infrastructure) ◀─ 메타데이터 시스템, 모니터링 도구 │
└────────────────────────────────────────────────────────┘
```

원칙 (Principle)데이터를 관리하기 위한 전사적 표준 가이드라인, 보안 표준, 명명 규칙(Naming Rule)을 정의합니다.
* 조직 (Organization)데이터 관리에 책임을 지는 주체들을 정의합니다.
* 데이터 거버넌스 위원회: 전사 데이터 표준 및 정책을 심의·의결하는 최고 기구입니다.
* 데이터 스튜어드 (Data Steward, 데이터 관리자): 현업 관점에서 비즈니스 데이터의 품질을 직접 모니터링하고 가이드라인을 전파하는 실무 주체입니다.
* 프로세스 (Process)데이터의 생성, 변경, 만료에 이르는 전체 라이프사이클을 통제하는 표준 승인 절차입니다.
* 인프라 (Infrastructure)거버넌스 규칙이 상시 작동하도록 기술적으로 받쳐주는 IT 환경(메타데이터 시스템, 품질 모니터링 대시보드, 데이터 리니지 흐름 뷰어)입니다.

## 📌 2. 데이터 표준화 체계 및 메타데이터 구축

전사 분산 데이터베이스 내 동일한 성격의 데이터들이 저마다 다른 이름이나 형식으로 방치되는 것을 막기 위한 기술적 도구들입니다.

### (1) 데이터 표준화의 3대 요소

표준화 구성요소주요 정의구체적인 실무 적용 예시**표준 단어 (Word)**사내 업무에서 사용되는 단어들의 동의어를 제어하고 단어를 하나로 통일합니다."고객번호"와 "회원ID"가 혼용되지 않도록 **"고객ID"**로 표준명 단일화**표준 도메인 (Domain)**컬럼이 가질 수 있는 데이터 타입, 데이터의 길이, 허용 조건 범위를 사전 설정합니다.모든 날짜 데이터는 **"CHAR(8)의 YYYYMMDD 포맷"**으로 강제 규격화**표준 코드 (Code)**데이터 값으로 들어올 수 있는 범주형 코드를 사전에 공통 코드로 등록하고 제어합니다.성별 코드는 오직 **"M(남), F(여)"**만 입력 가능하도록 공통 제약 설정


### (2) 메타데이터 (Metadata) 및 데이터 리니지 (Data Lineage)

* 메타데이터 (Metadata): '데이터를 설명하는 상위 데이터'로, 테이블 명세서, 컬럼 구조, 스키마 형태 등이 기록되는 핵심 자산 정보 데이터베이스입니다.
* 데이터 리니지 (Data Lineage): 데이터가 원천 데이터베이스로부터 출발해 어떤 수집 솔루션을 통과하고, 어떤 ETL 변환($MapReduce$) 작업을 거쳐 분석 리포트까지 이동했는지 그 흐름과 족보를 역추적(Lineage Tracking)할 수 있는 계층적 흐름 구조입니다.이점: 특정 저장 데이터에서 왜곡이 발견되었을 때, 상위의 수집 단계 중 어느 위치에서 장애가 터졌는지 파악하기 위한 '영향도 분석'에 절대적인 이정표 역할을 수행합니다.

## 📌 3. 정형 데이터 품질 관리 표준 5대 지표 및 수리적 공식

데이터의 정합성과 비즈니스 무결성을 수학적으로 평가하고 측정하기 위한 품질 관리 표준 프레임워크입니다.

```text
[데이터 품질 5대 지표 관계도]
┌───────────────────┐    ┌───────────────────┐
│     완전성 (C)    │    │     유일성 (U)    │
│  필수필드 Null 통제 │    │   중복 레코드 배제  │
└─────────┬─────────┘    └─────────┬─────────┘
          │                        │
          └───────────┬────────────┘
                      ▼
             ┌───────────────────┐
             │     유효성 (V)    │ ── 도메인/형식 범위 준수
             └────────┬──────────┘
                      ▼
             ┌───────────────────┐
             │     일관성 (Co)   │ ── 시스템 간 상호 일치
             └────────┬──────────┘
                      ▼
             ┌───────────────────┐
             │     정확성 (A)    │ ── 실제 참값과의 일치
             └───────────────────┘
```

하여금 오류를 방지할 수 있도록 하는 성질

### (1) 완전성 (Completeness)

* 정의: 수집된 전체 레코드 중 반드시 채워져야 하는 필수 데이터 컬럼에 누락(Null 또는 공백)이 없이 입력된 정도입니다.
* 수식:완전성(%)=(1−전체 대상 건수필수 필드의 Null 건수)×100

### (2) 유일성 (Uniqueness)

* 정의: 고유한 식별 키를 지닌 레코드가 중복되어 쌓이지 않고, 유일한 고유값으로 존재하는 정도입니다.
* 수식:유일성(%)=(1−전체 대상 건수중복 발생 레코드 건수)×100

### (3) 유효성 (Validity)

* 정의: 데이터 값이 사전에 선언된 비즈니스적 물리적 범위, 정규식 규칙, 데이터 도메인을 정확히 준수하여 입력된 비중입니다.
* 수식:유효성(%)=(1−전체 대상 건수도메인 표준 포맷 위배 건수)×100

### (4) 일관성 (Consistency)

* 정의: 데이터베이스 내의 서로 다른 테이블이나 분산된 타 시스템 간에 동일한 정보를 나타내는 데이터들이 논리적 모순 없이 완전히 일치하는 수준입니다. (예: 마스터 테이블의 고객 상태정보와 주문 테이블의 고객 결제정보 간 논리적 연계성 일치 여부)
* 수식:일관성(%)=(1−전체 대상 건수정합성 불일치 데이터 건수)×100

### (5) 정확성 (Accuracy)

* 정의: 데이터베이스에 적재된 수치가 가상의 예측치나 임의의 오류가 아닌, 실제 오프라인 현실 세계에 존재하는 정답 실측값(True Value)과 정확하게 물리적으로 부합하는 지표입니다.
* 수식:정확성(%)=(1−전체 대상 건수물리적 오차 및 데이터 왜곡 건수)×100

## 📌 4. 개정 데이터 3법 및 개인정보 거버넌스 기획

빅데이터 플랫폼을 구축할 때 가장 강하게 충돌하는 법적·규제적 제약 요소를 안전하게 통제하기 위한 제도적 장치입니다.

### (1) 데이터 3법(개인정보보호법, 신용정보법, 정보통신망법) 개정의 핵심 취지

* 핵심 골자: 데이터 경제 활성화를 도모하기 위해 수집된 데이터 중 특정 개인을 완전히 식별할 수 없도록 마스킹 및 해시 가공 처리된 "가명정보" 개념을 명확히 명문화했습니다.
* 법적 허용 요건: 가명정보로 가공된 개인정보는 정보주체의 사전 동의(Consent) 없이도 ① 통계작성(상업적 목적 포함), ② 과학적 연구(산업적 연구 포함), ③ 공익적 기록 보존 목적에 한해 유연하게 자유 활용할 수 있도록 규제의 빗장을 해제해 주었습니다.

### (2) 가명정보(Pseudonymized) vs 익명정보(Anonymized)

개정 법률 하에서 두 개념은 법적 보호 한계 영역이 철저하게 다릅니다.

```text
[정보의 식별성 및 법적 규제 스펙트럼]
┌─────────────────────────────────┐   ┌───────────────────────────────┐
│     가명정보 (Pseudonymized)    │   │      익명정보 (Anonymized)    │
│  - 추가 정보 결합 시 식별 가능   │   │  - 어떠한 수단으로도 식별 불가│
│  - 개인정보보호법 통제 [적용]     │   │  - 개인정보보호법 통제 [제외]  │
└─────────────────────────────────┘   └───────────────────────────────┘
```

* 가명정보 (Pseudonymized Data):정의: 개인정보의 일부를 암호화하거나 변경하여, "추가적인 제3의 정보의 결합이나 복호화 키 없이는" 특정 개인을 알아볼 수 없도록 조치한 상태입니다.
* 법적 지위: 여전히 추가 정보 결합 시 유추 가능성이 열려 있는 '개인정보' 범주에 포함되므로, 유실 및 탈취 시 사후적인 법적 책임이 따르며 안전성 확보 조치(접근 통제, 키 관리 등)를 강력히 수행해야 합니다.
* 익명정보 (Anonymized Data):정의: 가용한 모든 기술과 물리적 수단을 전부 동원하더라도, **"다른 어떤 데이터와 결합하더라도 다시는 특정 개인을 유추·식별할 수 없는 수준"**으로 영구 변환이 완료된 상태입니다.
* 법적 지위: 개인정보보호법의 적용 범주에서 원천적으로 '완전히 제외'되므로, 사후 규제 없이 완벽하게 제3자 제공 및 마케팅 비즈니스 분석 자원으로 자유롭게 활용이 허용됩니다.

### (3) 마이데이터 (MyData) 비즈니스와 개인정보 전송요구권

* 개인정보 전송요구권: 정보주체(개인)가 "내 신용정보와 거래정보를 기존 금융기관에서 마이데이터 혁신 분석 기업으로 안전한 보안 망(Standard API)을 통해 전송하라"고 명령할 수 있는 주체적인 권리입니다.
* 비즈니스적 효과: 기업들이 정보 독점 체계에서 벗어나 개인의 주도적인 가공 요청 하에 금융 자산 포트폴리오 최적화 추천, 맞춤형 지능적 상품 매칭 서비스 등 초개인화된 분석 서비스를 제공할 수 있는 법적 가교 역할을 지탱하게 되었습니다.

### (2) 하둡 에코시스템 3대 수집 기술 메커니즘 비교

빅데이터 인프라 시험 문제에서 성능 지표와 구조적 차이를 파고드는 단골 출제 대상입니다.

* Apache Flume (로그 지향 분산 수집):아키텍처: Source→Channel→Sink의 3단 트랜잭션 버퍼 구조입니다.
* 유실 방지: $Source$와 $Sink$ 사이에서 데이터를 안전하게 중계하기 위해 메모리 채널($Fast$, 휘발성) 또는 파일 채널($Slow$, 영속성)을 두어 안정적 트랜잭션을 보증합니다.
* Apache Sqoop (관계형 DB ↔ 하둡 벌크 이식):아키텍처: Map-Only 기반 분산 처리 적재 기술입니다.
* 특징: 중간에 리듀스($Reduce$) 과정이 전혀 없기 때문에 병목 현상이 현저히 낮으며, SQL 쿼리를 활용해 고속 대량 이적재를 구현합니다.
* Apache Kafka (분산 메시징 플랫폼):아키텍처: Producer→Topic (Partition)→Consumer 및 관리용 $ZooKeeper$ 구성입니다.
* 특징: 고성능 분산 파티션 구조와 파일 시스템 순차 적재(Append-Only) 방식을 통해 디스크 I/O 속도를 하드웨어 한계까지 끌어올립니다.

## ⚡ 2. [1-3-2] HDFS 저장 인프라와 NoSQL 아키텍처 코어

하둡 HDFS의 안정성 제어 원리와 수평적 확장을 지배하는 분산 저장 표준 매커니즘 요약입니다.

### (1) HDFS 네임노드 이중화 및 체크포인팅 과정

네임노드가 단일 실패 지점($SPOF$)이 되는 인프라적 치명상을 해결하기 위해 구동되는 정교한 아키텍처입니다.

* FsImage & EditLog 체크포인팅:$FsImage$는 메모리 전체 디렉터리 스냅샷이며, $EditLog$는 스냅샷 생성 이후 발생한 실시간 쓰기/수정 이력 로그 파일입니다.
* 합병 과정: 세컨더리 네임노드(Secondary NameNode)가 일정 주기마다 주기적으로 네임노드의 $EditLog$를 가져와 $FsImage$에 병합($Checkpointing$)해 줌으로써 네임노드 부팅 메모리 로드 시간을 비약적으로 낮춰줍니다.
* 고가용성 이중화 (HA):실시간 복구를 위해 $Active$ 네임노드와 $Standby$ 네임노드가 실시간 저널노드($JournalNode$) 클러스터를 공유하며 메타데이터 정합성을 상시 일치시킵니다.
* 주키퍼($ZooKeeper$)가 헬스체크($Heartbeat$)를 상시 감시하다가 $Active$ 다운 시 즉각 $Active$ 승격($Failover$)을 통제합니다.

### (2) CAP 이론 vs BASE 원칙 의사결정 매트릭스

분산 데이터베이스 아키텍처 설계의 타협 불가능한 한계점과 실무적 적용 노선입니다.

* ```text
[CAP 이론의 3대 가치 상호 배타성]
                        일관성 (Consistency)
                               / \
                              /   \
                             /  CA \
                            /       \
             일관성+가용성 (RDB)      일관성+분할용인 (HBase)
                          /   CAP     \
                         /             \
      가용성 (Availability) ─────────── 분할용인 (Partition Tolerance)
                               AP
                        가용성+분할용인 (Cassandra)
```

Consistency (일관성): 분산 클러스터 내의 임의의 노드에 쓰기 연산이 완료되면, 즉각 다른 모든 노드에서 똑같이 업데이트된 값을 읽을 수 있어야 합니다.
* Availability (가용성): 일부 노드에 하드웨어 장애가 터지더라도, 시스템 전체는 멈추지 않고 항상 정상적으로 읽기/쓰기 응답을 돌려주어야 합니다.
* Partition Tolerance (분할용인): 네트워크 통신 두절로 노드 간 통신이 끊어지더라도 독립적으로 서비스가 구동되어야 합니다. (※ 현대의 대규모 분산 클러스터에서는 네트워크 물리 장애를 전제하므로 P는 항상 기본 탑재되어야 하며, 아키텍트는 결국 CP나 AP 중 하나만 선택할 수 있습니다.)
* BASE 원칙 (Basically Available, Soft-state, Eventual consistency):고수준의 엄격한 트랜잭션 원칙인 ACID를 내려놓고, 시스템 가용성을 최우선으로 확보하기 위해 비동기 백그라운드 복제를 적용합니다.
* 쓰기 직후엔 일시적 데이터 불일치(Soft-state)를 허용하되, 최종적으로 일정 시간이 흐르면 완벽히 동기화(Eventual consistency)되는 절충적 아키텍처 노선입니다.

### Q1. [데이터 척도] 다음 중 데이터의 측정 척도에 대한 설명으로 가장 적절하지 않은 것은?

* ① 성별이나 혈액형과 같은 명목 척도는 단순 분류 목적으로, 사칙연산뿐만 아니라 대소() 비교 연산도 불가능하다.
* ② 학점이나 만족도와 같은 서열 척도는 값들 사이에 순서와 우열 관계가 존재하며, 측정 단위 간의 간격이 항상 일정하다는 특징을 가진다.
* ③ 온도는 절대영점(0이 없음을 의미함)이 존재하지 않는 대표적인 등간 척도로, 덧셈과 뺄셈은 가능하지만 곱셈과 나눗셈은 불가능하다.
* ④ 키, 몸무게, 매출액은 절대영점이 존재하는 비율 척도로 사칙연산(+,−,×,÷)이 모두 허용되는 가장 상위의 척도이다.**← 클릭하여 정답 및 해설 확인**
* 정답: ②
* 해설: 서열(순서) 척도는 값들 사이에 순서와 우열 관계는 존재하지만, 측정 단위 간의 간격이 일정하지 않습니다. 간격이 일정한 성질을 가진 척도는 등간 척도와 비율 척도입니다.

### Q2. [엔터프라이즈 시스템] 기업 내의 다양한 비즈니스 소스 데이터 원천에 대한 설명 중 가장 적절하지 않은 것은?

* ① SCM(공급망 관리)은 제품의 원재료 조달부터 제조, 유통, 최종 소비자 전달까지의 모든 공급망 흐름을 통합 관리하여 비용을 최적화한다.
* ② ERP(전사적 자원 관리)는 인사, 재무, 제조 등 기업의 전체 경영 자원을 하나의 데이터베이스로 통합하여 실시간 관리하는 전사 시스템이다.
* ③ CRM(고객 관계 관리)은 고객 정보를 통합적으로 분석·저장하여 고객의 만족도와 충성도를 제고하는 경영 기법 및 솔루션이다.
* ④ DW(데이터 웨어하우스)는 현업 부서나 특정 사용자의 목적에 맞게 필요한 데이터만을 원천 DB로부터 추출하여 구축한 소규모 맞춤형 접근 계층이다.**← 클릭하여 정답 및 해설 확인**
* 정답: ④
* 해설: 현업 부서나 특정 사용자의 목적에 맞게 소규모 맞춤형으로 구축한 데이터 저장소는 **DM(Data Mart, 데이터 마트)**에 대한 설명입니다. DW(데이터 웨어하우스)는 기업 전반의 다양한 원천 DB의 데이터를 공통 형식으로 변환하여 통합한 대규모 시계열 이력 데이터베이스입니다.

### Q3. [아파치 플럼] 아파치 플럼(Apache Flume)의 아키텍처와 데이터 유실 방지 메커니즘에 대한 설명으로 가장 적절하지 않은 것은?

* ① 플럼은 대량의 로그 데이터를 수집하기 위해 Source → Channel → Sink의 3단계 레이어 구조를 운용한다.
* ② Source는 외부 원천으로부터 로그 데이터를 수집하여 이벤트를 포맷팅한 후 중간 버퍼인 Channel로 전달한다.
* ③ Channel은 Source와 Sink 사이에서 이벤트를 임시 보관하며, 무조건 물리 디스크가 아닌 메모리(Memory)에만 데이터를 적재하여 유실을 원천 차단한다.
* ④ Sink는 Channel로부터 데이터를 이어받아 HDFS, HBase 등의 최종 목적지 저장소에 적재(Commit)를 실행한다.**← 클릭하여 정답 및 해설 확인**
* 정답: ③
* 해설: 플럼의 채널(Channel)은 메모리(Memory Channel)뿐만 아니라 파일(File Channel) 형태로도 지정할 수 있습니다. 시스템 장애 시 유실을 원천 차단하고 영구성을 보장하기 위해서는 메모리가 아닌 물리 디스크(File Channel) 방식을 채택해야 합니다.

### Q4. [아파치 스쿱] RDBMS와 하둡 간 데이터 전송 솔루션인 아파치 스쿱(Apache Sqoop)에 대한 설명으로 가장 올바른 것은?

* ① 스쿱은 수집 및 적재 시 하둡 클러스터의 자원을 효율적으로 쓰기 위해 맵(Map) 단계와 리듀스(Reduce) 단계를 완벽히 병렬 실행한다.
* ② 관계형 데이터베이스(RDBMS)의 정형 데이터를 HDFS로 적재할 수만 있으며, 반대로 하둡의 데이터를 RDBMS로 내보내는 것은 불가능하다.
* ③ 분산 병렬 적재 시 데이터의 정합성 붕괴를 막고 균등 분할을 실행하기 위해 대상 테이블의 기본 키(Primary Key) 컬럼을 활용한다.
* ④ 스쿱은 비정형 데이터인 시스템 로그나 동영상 등의 스트리밍 데이터를 실시간으로 감지하여 HDFS에 밀어넣는 데 특화되어 있다.**← 클릭하여 정답 및 해설 확인**
* 정답: ③
* 해설: 스쿱은 여러 맵 태스크가 병렬로 데이터를 분할 수집할 때 데이터 왜곡을 방지하기 위해 기본 키(Primary Key)를 기준으로 데이터를 균등 파티셔닝합니다.오답 정리:① 스쿱은 집계 연산이 필요 없으므로 리듀스 단계 없이 오직 Map-Only로만 작동합니다.
* ② RDBMS에서 하둡으로의 가져오기(Import)뿐만 아니라 하둡에서 RDBMS로의 내보내기(Export) 양방향 모두 완벽히 지원합니다.
* ④ 스쿱은 정형(관계형) 데이터를 일괄 처리(Batch) 방식으로 전송하는 도구이며, 비정형 실시간 수집에는 적합하지 않습니다.

### Q5. [아파치 카프카] 대용량 실시간 분산 메시징 플랫폼인 아파치 카프카(Apache Kafka)에 대한 설명으로 가장 적절하지 않은 것은?

* ① 발행-구독(Publish-Subscribe) 모델 아키텍처를 따르며, 메시지를 보내는 Producer와 메시지를 소비하는 Consumer로 주체가 분리된다.
* ② 카프카의 Broker는 전송받은 메시지를 분산 저장하며, 메모리가 아닌 디스크에 메시지를 파일로 보존하여 높은 신뢰성과 영구성을 제공한다.
* ③ 분산 코디네이션 서비스인 ZooKeeper(주키퍼)와 유기적으로 연동하여 카프카의 메타데이터 관리 및 브로커의 상태를 제어한다.
* ④ Consumer가 데이터를 소비하고 나면 해당 메시지는 즉시 카프카 큐(Queue)에서 영구적으로 완전히 자동 소멸된다.**← 클릭하여 정답 및 해설 확인**
* 정답: ④
* 해설: 카프카는 전통적인 메시지 큐와 달리 Consumer가 데이터를 소비하더라도 메시지가 즉각 삭제되지 않고, 설정된 보존 기간(Retention Period) 동안 디스크에 파일로 안전하게 영구 저장됩니다. 이 덕분에 여러 컨슈머 그룹이 동일한 데이터를 반복해서 소비하는 재처리(Replay)가 가능합니다.

### Q6. [HDFS 아키텍처] 하둡 분산 파일 시스템(HDFS)의 메커니즘과 동작 원리에 대한 설명으로 가장 적절하지 않은 것은?

* ① 대용량 파일을 기본 128MB 단위의 블록(Block) 크기로 분할하여 클러스터 노드들에 분산 저장한다.
* ② 랙 인식(Rack Awareness) 알고리즘을 적용하여 기본 3벌(Replication Factor=3) 복제본을 서로 다른 랙의 데이터노드에 분산 배치함으로써 고장 감내성을 확보한다.
* ③ NameNode는 파일 디렉터리 구조 및 블록의 위치 정보가 포함된 메타데이터를 로컬 디스크가 아닌 물리 메모리(Memory) 상에 적재하여 고속 제어한다.
* ④ DataNode는 슬레이브 노드로서 디렉터리 메타데이터를 실시간 동기화하여 관리하며, 주기적으로 마스터에게 체크포인트 이벤트를 전송한다.**← 클릭하여 정답 및 해설 확인**
* 정답: ④
* 해설: 메타데이터를 관리하고 제어하는 것은 마스터 노드인 NameNode의 독점적 권한입니다. 슬레이브 노드인 DataNode는 실제 물리 데이터 블록을 로컬 디스크에 읽고 쓰며, NameNode에게 주기적으로 생존 신고용 하트비트(Heartbeat)와 블록 리포트(Block Report)를 보낼 뿐 메타데이터 동기화를 수행하지 않습니다.

### Q7. [체크포인팅] HDFS의 메타데이터 관리 및 체크포인팅(Checkpointing) 과정에 대한 설명으로 옳은 것은?

* ① FsImage는 하둡이 구동되는 동안 발생하는 모든 파일 시스템의 등록, 수정, 삭제 등의 실시간 변경 이력이 누적되어 기록되는 로그 파일이다.
* ② EditLog는 하둡 분산 파일 시스템의 디렉터리 정보와 파일-블록 매핑 상태를 메모리에 보관하고 있는 최종 완전한 상태의 스냅샷 파일이다.
* ③ Secondary NameNode는 NameNode 장애 시 즉각 Active 상태로 전환되어 클러스터 세션을 무중단으로 이어받는 이중화 백업 서버이다.
* ④ 체크포인팅은 Secondary NameNode가 주기적으로 EditLog를 가져와 FsImage와 병합(Merge)한 후, 갱신된 새로운 FsImage를 NameNode에 전송하는 배치 연산이다.**← 클릭하여 정답 및 해설 확인**
* 정답: ④
* 해설: 체크포인팅은 Secondary NameNode가 주기적으로 NameNode의 EditLog와 FsImage를 전송받아 병합(Merge)한 뒤 최신 FsImage를 새로 만들어 NameNode에 돌려주는 필수적인 디스크 병목 제어 연산입니다.오답 정리:① 파일 시스템의 실시간 변경 이력을 기록하는 로그는 EditLog입니다.
* ② 메모리의 최종 스냅샷 정보를 보관하는 물리 파일은 FsImage입니다.
* ③ Secondary NameNode는 Active-Standby 이중화 서버가 아닙니다. 단지 병합 작업만 대신해 주는 배치 노드이며, Active-Standby 이중화를 지원하는 것은 HA(High Availability) 아키텍처의 Standby NameNode입니다.

### Q9. [CAP 이론 및 BASE] NoSQL 분산 아키텍처를 지배하는 CAP 이론과 BASE 원칙에 대한 설명으로 가장 올바르지 않은 것은?

* ① CAP 이론에 따르면 분산 시스템 환경에서 일관성(C), 가용성(A), 분할 내성(P)의 3가지 속성을 완벽히 동시에 모두 만족하는 것은 기계적으로 불가능하다.
* ② 네트워크 단선 장애(Partition)는 현실 세계에서 상시 발생하므로 분할 내성(P)은 필수적이며, 결국 분산 DB는 CP 또는 AP 모델 중 하나를 타깃 설계해야 한다.
* ③ BASE 원칙은 가용성(Basically Available)과 유연한 상태(Soft-state)를 지지하되, 최종 일관성(Eventually Consistent)을 포기하여 시스템 전송 지연을 완전히 허용하지 않는 엄격한 데이터 정합성 모델이다.
* ④ 관계형 데이터베이스(RDBMS)가 지향하는 ACID 트랜잭션 모델에 대비하여, NoSQL은 BASE 원칙을 통해 수평적 확장성(Scale-out)을 극대화하는 길을 선택했다.**← 클릭하여 정답 및 해설 확인**
* 정답: ③
* 해설: BASE 원칙은 가용성을 높이기 위해 실시간 일관성은 잠시 포기하되, 노드 간 비동기 복제를 통해 시간 경과 시 최종적으로 데이터 정합성이 일치하는 **최종 일관성(Eventually Consistent)**을 추구하는 모델입니다. 일관성을 일시적으로 양보하고 수평적 분산 처리 성능을 비약적으로 취하는 설계 사상입니다.

### Q10. [정형 품질 지표] 다음 중 수집·저장된 정형 데이터의 품질을 평가하는 5대 핵심 품질 지표와 물리적 측정 공식의 연결이 올바르지 않은 것은?

* ① 완전성 (Completeness): 필수 입력값으로 정의된 특정 필드 내에 존재하지 않아야 할 빈 값(Null) 데이터가 들어오지 않고 완전히 다 채워져 있는 비율측정 비율=1−전체 대상 데이터 건수Null 데이터 건수
* ② 유일성 (Uniqueness): 테이블 내 기본 키(PK)로 지정된 식별자 정보가 중복되지 않고 오직 단 하나만 온전히 존재하는 비율측정 비율=1−전체 대상 데이터 건수중복 데이터 수
* ③ 유효성 (Validity): 컬럼값들이 사전에 약속된 표준 도메인 형식이나 물리적인 허용 범위 내의 값으로 적합하게 들어와 있는 비율측정 비율=1−전체 대상 데이터 건수물리적 형식/범위 미준수 오류 데이터 수
* ④ 일관성 (Consistency): 현실 세계의 참값과 데이터베이스 내의 물리적 데이터 값이 오차 없이 완벽히 동일하고 정확하게 보존되어 있는 일치 비율측정 비율=1−전체 대상 데이터 건수실제 참값과 일치하지 않는 오류 데이터 수**← 클릭하여 정답 및 해설 확인**
* 정답: ④
* 해설: 현실 세계의 참값(정밀 물리 실젯값)과 일치하는 속성을 평가하는 품질 기준은 **정확성(Accuracy)**에 해당합니다. **일관성(Consistency)**은 서로 다른 정보 시스템 간에 혹은 부모-자식 테이블 관계(참조 정합성) 간에 상호 충돌이나 모순이 없이 논리적인 관계가 정교하게 준수되는지 평가하는 지표입니다.
